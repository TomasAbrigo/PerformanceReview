# Performance Review

In-house performance review tool replacing BambooHR's performance module. Data is ingested from Bamboo; this app is the system of record afterwards.

@AGENTS.md

## Stack

- Next.js 16 (App Router, `src/` dir, TypeScript strict, Cache Components + Partial Prefetching enabled), React 19
- Tailwind CSS v4 + shadcn/ui (style `base-nova`, Base UI primitives; `Form` is replaced by `Field` in this shadcn version)
- next-intl: locales `es` (default) and `en`, routes under `/[locale]`, routing in `src/i18n/`, locale proxy in `src/proxy.ts` (Next 16 `proxy.ts` replaces `middleware.ts`)
- Supabase (local, via CLI + Docker) for Postgres/Auth/Storage
- Drizzle ORM + `postgres` (postgres-js); `drizzle-kit` for migrations
- Vitest (projects `unit` and `db`) + Testing Library; Playwright for e2e
- pnpm 12, Node 24

## Conventions

- **TypeScript strict.** No `any`; prefer inferred Drizzle types (`$inferSelect` / `$inferInsert`).
- **Drizzle is SQL-first.** Schema lives in `src/db/schema/*.ts`; always change schema then `pnpm db:generate` and commit the generated SQL in `drizzle/`. Never edit applied migrations. `supabase/migrations/` does not exist today (the folder only holds `supabase/config.toml`); create it only if Supabase-specific SQL (RLS policies, extensions, functions) is ever needed, never for tables Drizzle owns.
- **DB access** goes through `src/db/client.ts` (`db` is lazy; use `closeDb()` in scripts/tests).
- **TDD: red, green, refactor.** Write a failing test first, make it pass, then refactor. Unit tests next to the code; DB tests are `*.db.test.ts`; e2e in `e2e/`.
- **i18n: every user-facing string is a message key** in `src/messages/{es,en}.json` (both files must have identical keys; a test enforces it). No hardcoded UI text. Use `Link`/`redirect` from `src/i18n/navigation.ts`, not `next/link`.
- **Authorization is one place per concern.** Who sees what in the insights views lives in `src/modules/insights/authz.ts` (pure; roles `hr`, `manager`, `employee`, `direction`): queries and pages ask it, none re-derives a rule from `actor.role`. Imports, data quality and settings are People-only: pages go inside `HrOnly` (`src/components/access`), server actions through `onlyHr` / `requireHr` (`src/modules/actor`). Settings (thresholds, minimum n, semester cuts) are `app_setting` rows with defaults in `src/modules/settings/definitions.ts`; change them with `setSetting` / `updateSettings`, which write `admin_audit_log`.
- **UI scope: insights plus the data it needs.** The app has `/insights/*`, `/imports/*`, `/data-quality/*` and `/settings/insights`; the sidebar and the home share one structure, `navGroups`: **Goals** (`/goals`) and **Assessments** (`/assessments`) first, as the two things people come for (the individual goals, and the questions and answers per cycle with the goals of the period beside them), then the **Análisis** (the `/insights/*` views, aggregated, never mixed with those two), then Datos and Configuración (only for People). Who may open Goals and Assessments is `individualScope` (`src/modules/actor/individual-scope.ts`: People all, a manager their team and themself, an employee themself, direction and an actor without a person none); inside, every request and answer still goes through `canRead`. The v1 screens (people, org chart, cycles, team goals, dashboards, templates and scales) were removed in #54 and #92: their tables, the `/api/v1` API and the CSV exports remain, but do not add screens for them back without a new decision.
- **Source IDs from Bamboo are preserved** (store them as-is in dedicated source-id columns next to our own UUID primary keys) so re-ingestion is idempotent and traceable.
- Env vars: local values in `.env.local` (gitignored); keep `.env.example` in sync. `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` are reserved for Supabase Auth (v2) and unused today. e2e: `E2E_DATABASE_URL` (default: `DATABASE_URL` with `_e2e` appended to the database name) and `E2E_PORT` (default 3100).
- **UI follows the Santex brand kit** (light mode): tokens in `src/app/globals.css` (teal scale as `brand-*`, status pairs, chart colors), Chakra Petch Light for headings (base `h1`-`h3`, never bold) and Inter for body; the `.kicker`, `.stat-value`, `.control`, `.segmented` and `.button-outline` classes are the shared pieces. Screens use `PageHeader` (`src/components/page-header.tsx`) and `Panel` (`src/components/insights/parts.tsx`); the sidebar and the home read the same `navGroups` (`src/components/nav/nav-items.ts`). The approved canvas (pen.dev, 2026-11-18) adds the shared surfaces in `src/components/experience.tsx` (`MetricCard`, `ProgressRing`, `IconTile`, `EmptyState`, `AdvancedFilters`, `UploadSteps`, `PageSkeleton`) and `CardCollection` (`src/components/card-collection.tsx`: a grid of `record-card` articles with the rest behind "Ver N registros más"); their classes live in `globals.css` (`.metric-card`, `.goal-card`, `.assessment-card`, `.filter-toolbar`, `.empty-state`, `.admin-surface`) and `src/app/visual-data.css` (`.record-grid`, `.comparison-grid`, `.delta-pill`). Lists of records are cards, not tables; long lists of people (hundreds) are dense rows (`.dense-list` / `.dense-row` in `visual-data.css`, inside a `CardCollection`); a data table, when kept, sits behind a "Ver como tabla" `details`. The sidebar follows the canvas component «Navegación por rol» (Inicio, PERSONAS, ANÁLISIS, ADMINISTRACIÓN; `side-nav-*` classes), and `Panel` takes an `icon` so non-chart panels say what they hold.
- **Drill-down and numbers with context (#117).** Every chart mark and KPI of an insights view opens "the data behind it" through the URL: a `DrillLink` (`src/components/drill/drill-link.tsx`; `StackedBar100`/`SentimentBars` take `drillOf`, `Matrix` cells and `MetricCard` take `drill`) sets `?drill=<kind>:<args>` (`src/modules/insights/drill-spec.ts`: `parseDrill`/`formatDrill`, kinds indicator, risk, theme, sentiment, completion, goals), and the page renders `DrillSection` (`src/app/[locale]/insights/drill-section.tsx`) in a Suspense boundary: it reads `drillRecords` (`src/modules/insights/drill.ts`, which applies `insightsScope` and the minimum group size; direction only gets masked counts, never names) and shows them in the side `DrillSheet`. A new kind: extend `Drill`, its parser and a reader in `drill.ts`. KPIs use `MetricCard` with `scale` (a `ScaleBar` on 1–5 or 0–100 %), `status` (`likertTone`/`percentTone` in `src/modules/insights/tone.ts`, from `alerts.riskThreshold` and `targets.*` settings) and `delta` vs. the previous cycle; panels take `kind` (their icon, `src/components/charts/panel-icons.tsx`) and `tone="highlight"`; themes are shown with `useThemeLabel` (`Themes` messages), never the raw key.
- **One cycle across the app, targets on the bars (#119).** A screen opens on the cycle its URL asks for, else the one last chosen in any screen, else the first of its list: `pickCycle` (`src/modules/review-core/current-cycle.ts`) with `rememberedCycle()` (`remembered-cycle.ts`, the `pr_cycle` cookie that `CycleMemory` in the layout writes whenever the URL carries `cycle`); lists built from `listCycles` go through `latestFirst` (latest period first, never creation order). Screens show `cycleName` (a period of ISO days reads as months, "mar – sept 2026"); files keep `storedCycleName`. A percent or Likert KPI passes `scale.target` (`percentTarget` / `likertTarget` in `src/modules/insights/tone.ts`) so the bar marks where "on target" starts; a count has no bar unless its scale is its own total; only a card at risk has the coloured edge. The home is `HomeSignal`: the cycle in focus with its progress, then what to attend (each row with its action), then the cycle's KPIs; the directory of sections stays at the foot. "Vencido" has one rule everywhere (the goals list, the home, the goal analytics and their exports, the executive view and the Arturía report): in progress and due before the cycle's reference date (`goalAsOf` in `src/modules/goals/state.ts`: today while the period runs, the end of the period once the cycle is closed, because the goals' snapshot is frozen there; the analytics read it from `GoalContext.asOf`, `/goals` from `cycleGoalAsOf` when it lists a cycle). The four goal states are a partition (an overdue goal is not "en curso": the parts add up to the total), and a completion rate shown against a target counts only the goals due by that date (`completedDuePct`); a screen that shows all the goals says so in its label and carries no target. A flat delta (0) shows a dash, not an arrow. In Spanish the word is always "objetivo", never "goal".
- **The real question set (#123).** The Santex system template (`src/modules/templates/seed.ts`, `santex_semester`) holds exactly the questions Santex runs in Bamboo today, nothing more, nothing less: employee valued 1-4, best work (one option), strengths, improvement, social impact (`custom_1`), environmental impact (`custom_2`), information security (Sí/No); manager strengths, improvement, frequent conversations (Sí/No), retention and engagement (Likert 1-5, hidden). The raw report fixtures carry the same custom questions in every cycle with Sí/No answers; a bare yes/no is never a comment to analyse (`YES_NO` in `src/modules/qualitative-analysis/analysis-text.ts`); `custom_<n>` is labelled with its question text. The seeder rewrites an outdated system template in place. To add or drop a question, change the seed, the fixture questions (`src/fixtures/company/questions.ts`) and the tests together.
- shadcn components live in `src/components/ui` (excluded from Prettier); add more with `pnpm dlx shadcn@latest add <name>`.

## Hard rule: no deploy, local only

Do **not** deploy anywhere, do **not** run `vercel`, and do **not** link or modify a Vercel/Supabase cloud project. Everything runs locally against the Docker Supabase stack. (`.mcp.json` points to a Supabase MCP server; do not use it to modify remote projects.)

## Git and GitHub workflow

The owner asked that everything lives on GitHub (`TomasAbrigo/PerformanceReview`). Pushing is allowed and expected:

- One branch per issue, named `tomas/issue-<n>-<short-desc>`, based on `main`.
- Commit with conventional messages referencing the issue, push the branch (`git push -u origin <branch>`) and open a PR against `main` with `gh pr create` whose body contains `Closes #<n>` (or `Part of #<n>` for partial slices).
- The orchestrator merges PRs; do not merge your own PR, do not push to `main` directly, never force-push.
- CI (`.github/workflows/ci.yml`) runs on every PR and push to `main`: `checks` (typecheck, lint, format:check, unit), `db-tests` (postgres:17 service, `pnpm test:db`, `pnpm build`) and `e2e` (Playwright; CI installs the browser with `pnpm exec playwright install --with-deps chromium`, locally `pnpm exec playwright install chromium` is enough). Run `pnpm check` before pushing; PRs should be green before the orchestrator merges.
- Jira is not used for this repo for now.
